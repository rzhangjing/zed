# 设计说明（精简版）

## 1. 目标

在宿主软件内部记录**用户发起**的操作，供事后查看「谁在什么时候做了什么、结果如何」。

必须满足：

* 接入成本低：一处调用，不改变业务代码结构；
* 不影响交互：记录动作不能卡住界面或请求；
* 部署简单：单文件数据库，随程序走，不需要额外服务；
* 可查询：按人、按动作、按时间、按关键字能查出来；
* 可清理：长期运行不能无限膨胀。

非目标（明确不做）：防篡改存证、合规级审计、跨机集中采集、操作回放、字段级加密。

## 2. 为什么只记录用户操作

需求边界是「用户的操作」。系统自己执行的动作（定时任务、启动初始化、内部补偿、重试）
对使用者没有追溯价值，反而会淹没真正的用户行为。

实现上不加 `actor_type` 字段、不做运行时判断，而是**用调用点划边界**：
只有用户触发的入口（点击、提交、确认框回调）才调用 `recorder.log()`。
系统路径不调用，因此也不需要「过滤系统事件」的逻辑和配置。

## 3. 结构

```
业务代码（用户触发）
   │ OperationLog（不含时间）
   ▼
Recorder::log ── 校验/截断/打时间戳 ──► 有界队列（默认 4096）
                                          │ 满了 → 丢弃 + dropped 计数
                                          ▼
                                 写入线程（单线程）
                                   │ 有积压才合批（默认 256）
                                   │ 时间戳取 max(now, 上一条+1µs)
                                   │ 单事务批量 INSERT
                                   ▼
                                 SQLite（WAL）
```

* 调用方线程只做校验、打点和入队，耗时微秒级；
* 写入线程独占数据库写连接，事务按批提交；
* 查询走同一把连接锁，与写入互斥但时间很短。

## 4. 数据模型

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `occurred_at` | INTEGER PK | 发生时间，Unix 微秒；即记录的主键 |
| `user_id` | TEXT | 操作人，必填 |
| `user_name` | TEXT | 显示名，可选 |
| `action` | TEXT | 做了什么，必填，建议用动词短语 |
| `target` | TEXT | 对象，如 `order:O-88231` |
| `result` | TEXT | 结果，如 `成功`、`失败：无权限` |
| `detail` | TEXT | 附加信息，超 4096 字符截断 |

索引：

* `(user_id, occurred_at DESC)`：看某个人的操作；
* `(action, occurred_at DESC)`：看某个动作的执行情况；
* 时间排序、范围查询、游标翻页直接用主键，不需要额外时间索引。

### 为什么时间戳可以做主键

用户不可能在同一微秒内执行两次操作，时间戳天然唯一。省掉自增 id 后：

* 排序就是主键顺序，范围扫描直接走 B 树；
* 翻页游标用「上一页最后一条的时间」，无需 `OFFSET`；
* 清理按时间前缀删除，语义直观。

时钟粒度或回拨可能让「now」重复，所以写入线程维护一个水位：

```
occurred_at = max(now, 上一条 occurred_at + 1µs)
```

正常操作间隔远大于 1µs，结果等于真实时间；突发写入时最多比真实时间晚若干微秒，
换来的是主键永远唯一、永不丢记录。

## 5. 写入语义

| 行为 | 语义 |
| --- | --- |
| `log()` 返回 `Ok` | 已入队，未必已落库 |
| 队列满 | 返回 `QueueFull`，本条丢弃，`stats().dropped` 累加 |
| `flush()` | 等到此前入队的记录全部提交 |
| `close()` | 关闭队列 → 写入线程读完剩余记录 → 提交 → 退出 |
| 忘记 `close()` | 最后一个句柄析构时同样排空并刷盘 |
| 单批写入失败 | 立即重试一次；仍失败则整批计入 `failed`，记录 `last_error()` |

合批策略：写入线程收到第一条后，若队列还有积压就继续取，直到达到 `batch_size` 或取空；
取空立即提交。低峰期是「一条一事务」（延迟低），高峰期自动变成大批次（吞吐高），
不需要定时刷新，也不会为了攒批人为等待。

## 6. 查询

支持等值条件（操作人、动作）、时间范围、关键字模糊匹配（动作/对象/详情/操作人），
按 `occurred_at` 倒序返回，`before(上一页最后一条的时间)` 作为游标翻页。

`keyword` 使用 `LIKE '%kw%'`，只适合中低数据量；记录量大且需要全文检索时可在 SQLite 上启用 FTS5
（本版本未做，避免写放大和额外维护）。

## 7. 容量与留存

实测：单条约 190 字节（含索引与 WAL），写入约 6.4 万条/秒（NVMe、单线程批量）。

* 100 万条 ≈ 190 MiB；
* 10 万条/天 × 365 天 ≈ 3650 万条 ≈ 6.9 GiB。

留存建议：启动时调用一次 `prune_before(now - 90 天)`；清理后调用 `checkpoint()`
回收 WAL，需要的话再用 SQLite 工具执行 `VACUUM`。

## 8. 可靠性边界

* 进程崩溃：已提交事务不丢（`synchronous=NORMAL`）；进程内未提交的批次丢失，这是「不阻塞业务」的代价；
* 磁盘满：写入失败 → 重试 → 计入 `failed`，业务继续运行；监控 `failed` 与 `last_error()`；
* 多进程：SQLite 支持多读者单写者，多个进程同时写同一文件会互相 `SQLITE_BUSY`；
  而且时间戳水位是进程内的，多写者可能撞主键。请保证一个进程写，或每个进程用独立库文件；
* 数据被改：本方案不做防篡改，能访问数据库文件的人可以改记录。需要时在部署层做文件权限、
  备份校验或改用带签名的集中审计服务。

## 9. 扩展点

* 换存储：`Recorder` 内部只有 `Store` 一个依赖点，可以替换成 PostgreSQL/远端 HTTP；
* 加字段：在 `operation_log` 加列 + 调整 `insert_batch` / `query`，用 `PRAGMA user_version` 管理版本；
* 异步接入：`log()` 是同步的（只入队，不阻塞），可直接在 async 处理函数里调用；
  需要「记录成功才继续」时用 `flush()`；
* 权限控制：查询接口在应用层做鉴权，数据库文件本身给只读账号/加密盘。

## 10. 与复杂方案的区别

| 能力 | 本方案 | 复杂方案 |
| --- | --- | --- |
| 哈希链/防篡改 | 无 | 每条记录链式哈希 + 校验 |
| 存储抽象 | 直接 SQLite | Store trait + 多实现 |
| HTTP 中间件 | 无（业务里一行） | tower/axum 层 |
| 脱敏框架 | 无（由调用方控制 detail） | 按键名脱敏 + 限长 |
| CLI | 无（用任意 SQLite 工具） | 查询/校验/导出子命令 |
| 主键 | 时间戳（微秒） | 自增 id + 时间列 |

如果后续确实需要「不可篡改」「集中审计」，再按需加一层；当前版本先把「记录用户操作」
这件事做对、做小。
